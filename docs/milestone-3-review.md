## Findings and discrepancies

### Confirmed source and documentation findings

1. **Source directories are not independently packaged npm modules.** The [root manifest](../package.json) declares workspace globs, but the inspected apps/packages have no individual package manifests. Imports go directly to source files. The new guides describe this arrangement without inventing package export maps or separate package commands.
2. **HTTP composition includes business coordination and SQL.** [app.ts](../apps/api/src/app.ts) owns multi-line send membership checks/iteration, user/ledger reads and session deletion. [Fulfillment](../apps/api/src/fulfillment/service.ts) writes line SQL directly and imports service helpers. Shared [permission/audit](../apps/api/src/shared/audit.ts) imports `DomainError` from catalog. The architecture now qualifies desired thin-handler/ownership boundaries rather than claiming fully isolated modules.
3. **Polling interval is not a measured latency guarantee.** [App](../apps/web/src/app/App.tsx) schedules state refresh every two seconds, but requests may overlap and response time is not bounded to three seconds. [readState](../apps/api/src/service/readState.ts) and its [repository](../apps/api/src/service/repository.ts) load historical lines/orders without pagination. The earlier architecture statement that polling meets the three-second target was replaced with the actual mechanism and its limitation. No load/freshness experiment was run.
4. **Guided flag and navigation differ.** [Service.add](../apps/web/src/features/waiter/Service.tsx) opens choices when groups exist or multiple sizes exist, irrespective of `product.guided`. [saveCatalog](../apps/api/src/catalog/saveCatalog.ts) still validates the flag when required choices lack defaults. Milestone one's immediate-add behavior when guided mode is disabled therefore is not an accurate description of every current product. Milestone two introduced the current sequential workflow; no product decision about retaining the flag's old semantics is inferred here. No dedicated flag-off-with-defaults test was found. Historical specifications were preserved.
5. **Snapshots are protected from catalog maintenance, not every line edit.** [editLine](../apps/api/src/service/service.ts) recalculates and updates snapshots for allowed draft/submitted edits using historical product/pricing data. The architecture now makes that distinction; “immutable” should not be interpreted as prohibiting those explicit edits.
6. **Migration version 1 is idempotent DDL, not a skipped version block.** [migrate.ts](../apps/api/src/persistence/migrate.ts) executes the initial IF-NOT-EXISTS statements and conflict-ignore version insert on each call. Migration 2 has an explicit applied-version check. Persistence documentation now reflects this implementation.
7. **Graph enforcement is narrower than the full intended architecture.** [architecture.test.ts](../tests/architecture.test.ts) examines regex-matched relative static imports within web/src, checks cycles and rejects shared-to-feature imports. It is not complete module-boundary enforcement or a parser for all imports. AGENTS.md remains guidance for tools that read it.
8. **Aggregate response typing is frontend-owned.** [AppState](../apps/web/src/shared/api/api.ts) is a TypeScript definition with response casts, not a runtime shared response schema; integration tests import it from web code. This is documented as coupling, not changed.

### Suspected defects and investigation routes

- **Retry classification after a non-JSON proxy error:** [api.ts](../apps/web/src/shared/api/api.ts) awaits `response.json()` outside its fetch-error catch and before wrapping non-OK responses in `ApiError`. [useMutation](../apps/web/src/shared/api/useMutation.ts) retains retry metadata only for `ApiError` status 0/5xx. An HTML 502 response could therefore reach the generic error path and discard retry metadata for an uncertain mutation. The source path is confirmed; a browser reproduction and fault-injection regression are not part of this milestone. Existing [notes tests](../tests/notes.test.tsx) mock a rejected fetch and successful JSON, and [browser retry tests](../tests/e2e/workflow.spec.ts) exercise lost acknowledgements; neither establishes this non-JSON case.
- **Stale aggregate response ordering:** overlapping [App.refresh](../apps/web/src/app/App.tsx) calls have no request sequence/abort guard, unlike [usePreview](../apps/web/src/features/waiter/customize/usePreview.ts). A slower earlier state response might overwrite a newer one. This is a source-based concern, not a reproduced user incident. Investigate with deliberately reordered `/state` responses in a future implementation task.
- **Test database guard strength:** the integration setup checks whether the connection string contains `venue_test`, rather than parsing and comparing the database name. [Browser setup](../tests/e2e/setup.ts) uses a fixed isolated database and drops/recreates its schema. Follow the canonical isolated-database prerequisites; no guard/configuration change was made here.

### Coverage and historical record limits

[Integration tests](../tests/api.integration.test.ts) contain direct-permission, consumption rollback, retry, concurrent repeat, snapshot and migration cases, but they were **not executed** for this milestone. The representative permission test is not a complete role-by-route matrix. No dedicated component tests were found for Manager/CatalogForm/PolicyForm, Station, Field or Modal. Consumer/browser tests exist, so this is a gap in direct coverage, not a claim those components are entirely untested.

The dated [Milestone 2 verification record](milestone2-status.md) reports earlier integration/browser results and old graph enforcement wording. It remains historical evidence. This review and the current architecture qualify those claims without changing historical milestones to match the current tree.
