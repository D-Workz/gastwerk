# Gastro feature inventory

Inspection date: **2026-09-10**. Application: `/home/japtic/workspace/gastro_app/codex`, in the outer `gastro_app` Git repository. Inspected HEAD: `6d5b55437cd1578b64aa9f399f3a9ab5ff9a7932`, **plus the working tree**, not HEAD alone.

Gastro implements a single-venue restaurant workflow: managers maintain catalog and stock, waiters build and send orders, kitchen/bar staff prepare them, and waiters serve and close them. It includes meaningful recovery and historical-data mechanisms. It is not a payment, fiscal receipt, reservation or purchasing system.

This is an evidence inventory, not an application evaluation or a certification. Source paths, calls, SQL and test assertions were inspected. **No application tests, services, migrations, builds, package installations or evaluator runs were executed during this inventory.** Earlier test results from other tasks are not results for this inventory. Application files and READMEs were left unchanged; this document is the only deliverable.

## Reading the evidence

- **Connected**: a screen or command is wired through to implementation, as established by static tracing. This does not mean its runtime flow was exercised today.
- **Partial**: implementation exists, but an interface, operational step or important part of the claimed capability is missing or uncertain.
- **Documented only**: intent or an operator procedure exists without a corresponding implemented application flow or automation.
- Test references use the case IDs in the test index below. They describe assertions that would establish the stated behavior if executed successfully. **The “Run” column is No for every item.** “None found” means no focused case was located in the inspected suites, not proof that no indirect coverage exists.

The [architecture map][architecture], [user guide][users-doc], [API contract][api-doc], [configuration guide][config-doc], [extension guide][extensions], [Milestone 1][m1] and [Milestone 2][m2] were treated as intent and compared with implementation. Production intent comes from [deployment][deployment-doc] and [operations][operations-doc]. Historical reviews were used for leads, not accepted as current runtime evidence.

## Important discrepancies and uncertainties

1. **Usable source flow is not a current runtime pass.** Every feature status above is based on reading code and test assertions. Historical milestone pass counts are not reused. Owner topology, real catalog data, DB contents and deployed revision were not inspected.
2. **Retry durability has a specific uncovered failure path.** [api.ts][client-api] parses JSON before wrapping non-OK responses. An HTML 502 or malformed/truncated JSON can throw outside `ApiError`; [useMutation][client-mutation] then clears retained retry state rather than preserving uncertainty. This source path was confirmed; no incident/reproduction is claimed. Metadata is only saved after a classified uncertain failure, so closing/reloading while an initial request is still in flight is also not covered by the after-failure reload test.
3. **State freshness and close locking are bounded mechanisms.** Overlapping [App.refresh][app-web] calls have no response sequence guard. [closeOrder][order-service] reads `closed_at` before locking and does not reread it, unlike repeat's post-lock open-order check. Potential stale UI and duplicate concurrent close/audit effects need runtime investigation. No fix was made.
4. **Configuration UX and semantics have gaps.** Advanced product choices/sizes, categories/defaults/branding and users require JSON. `guided` remains server-validated but no longer determines frontend choice navigation. Optional Skip with a default reapplies the default. The advanced Customizer offers choices but no explicit optional-group clear control. These details are more precise than a blanket “all choices configurable in forms” claim.
5. **Historical protection needs precise wording.** Catalog edits do not rewrite saved lines; authorized edits do. Replacement uses current catalog but its UI starts from the old product. Migration 2 preserves tested known fields/snapshots, but schema parsing before a rename write does not guarantee preservation of unknown product fields. Closed totals can change if a manager uses the API to cancel a served closed-order line, since transition does not check closure and totals are computed on read; no UI flow or test for that case was found.
6. **Presentation is not data-access restriction or complete localization.** Manager-only history navigation does not mean only managers receive history in `/state`. Stations receive priced snapshots/catalog despite no order totals. Error localization is mostly generic and does not render the API's field errors. Raw event actions/IDs/JSON remain visible. Production login still contains a demo-only message.
7. **Operational automation is narrower than operations prose.** Backup/restore scripts exist, but no scheduling, retention, encryption, off-site copying, full recovery acceptance or automatic rollback exists. Preflight inspects the base Compose file, not arbitrary overlays. `check` omits API bundle/deployment scripts. [Extensions][extensions] calls Compose smoke a production restart test; the actual script points at development localhost:5173 and the default Compose stack.
8. **Scale and maintenance remain open.** Polling loads all historical lines/orders, manager stock reads all movements, cancelled station tickets accumulate, and requests/sessions lack cleanup. No load test or complete accessibility/security review was performed. Locks and indexes support particular invariants, not every possible concurrency claim.

## Features the owner may not know about

- **One more is price/recipe-aware:** it refuses a changed current configuration rather than silently reusing an obsolete price; sent items become new unsent work (U8/B2).
- **Notes protect the send workflow:** failed unsent-note saves block sending/navigation, and submitted notes require a deliberate amendment (U9).
- **Retry can recover after refresh:** a classified lost acknowledgement retains the original operation/key in the same tab; the non-JSON/in-flight limitations above matter (U18/S5).
- **One item can be split from a quantity-two line** for customization without changing its sibling (U10).
- **Serving sizes can override each option's recipe effects**, not merely scale a base recipe; refunds and rounding are configurable (U5/B1).
- **Reference ingredient cost is already calculated**, though there is no dedicated report screen for it (B3).
- **Served-item cancellation is a manager correction** with a minimum reason length and retained consumption; it is not a stock refund (U12/B6).
- **Production bootstrap refuses existing users**, and a separate script can test a backup restore without attaching to the running application database (V4/V9).
